Compliance gaps identified in the current system

HIGH Audit trail cannot record a reason for change

21 CFR 11.10(e); EU GMP Annex 11 §9

The audit-trail table has no column for the reason for change. Part 11 requires audit trails to record the reason where it is a predicate-rule requirement, and Annex 11 expects changes to GxP data to be justified. Reason is currently appended into a value column as free text, which is not queryable and not reportable.

Remediation. Add a REASON column (and a controlled reason-code list) to the audit table, require it on every change to a GxP record, and backfill or annotate historic rows. This is a data-model change, so it needs a data migration plan and re-validation of the audit-trail report.

Evidence: AUDIT_TRAIL

HIGH Database schema is altered automatically at startup

EU GMP Annex 11 §10 (change control); 21 CFR 11.10(a)

The ORM is configured to update the database schema on application start. The structure holding GxP records can therefore change without a change-control record, a review, or a migration script, and the change is invisible to the audit trail.

Remediation. Set the schema generation to validate-only, manage every structural change through versioned migration scripts under change control, and verify the schema as part of installation qualification.

Evidence: ddl-auto

HIGH Database console exposed in the running application

Annex 11 §12; data-integrity expectation

A web database console is enabled. It permits direct, unaudited modification of GxP data, which breaks the audit trail entirely.

Remediation. Disable the console in every environment above development and prove it is off as part of installation qualification.

Evidence: enabled

HIGH GxP timestamps come from the application server clock

21 CFR 11.10(e); EU GMP Annex 11 §9

Records are stamped with the application server's local time. Across multiple instances - which is exactly what a cloud migration introduces - clock drift and timezone differences make the sequence of GxP events unreliable, and contemporaneousness cannot be demonstrated.

Remediation. Take all GxP timestamps from a single authoritative source (the database clock or an NTP-synchronised UTC service), store them as UTC with an explicit offset, and document the time-synchronisation control.

Evidence: createUser, recordChange, applyDisposition, importFile, recordFailedImport, registerGeneratedCoa, enterResult, raiseOosDeviation (+4 more)

HIGH GxP record is modified without an audit-trail entry

21 CFR 11.10(e)

A write path to a regulated table does not reach the audit-trail service, so the change is not recorded.

Remediation. Route the write through the audit-trail service, or add database-level triggers, and add a test that fails when a GxP write has no audit row.

Evidence: recordFailedImport, purgeStaleImports

HIGH Credentials stored in configuration files

Annex 11 §12.4; general data-security expectation

Database or service credentials are present in configuration committed with the application.

Remediation. Move every credential to a managed secrets service, inject at runtime, and rotate anything that has been in version control.

Evidence: password, password

HIGH Shared administrator credential in configuration

21 CFR 11.10(d),(g); Annex 11 §12

An administrator username and password are stored in a configuration file and compared in plain text. A shared account means actions cannot be attributed to an individual, and a credential in a config file is readable by anyone with repository or filesystem access.

Remediation. Remove the credential from configuration, move to named individual accounts with role-based access, and keep any break-glass account in a secrets manager with check-out logging.

Evidence: password

MEDIUM Audit trail identifies the actor by free text

21 CFR 11.10(d); ALCOA++ Attributable

The audit trail stores the acting user as a plain string rather than a reference to the user table, so a renamed or deleted account breaks attributability of historic records.

Remediation. Store the immutable user id alongside the display name, and never delete user rows - deactivate them.

Evidence: CHANGED_BY

MEDIUM GxP data arrives over a host filesystem path

Annex 11 §4.8, §5 (data transfer checks)

Instrument data is read from an absolute local or UNC path. The transfer has no checksum or completeness check, and the path cannot be reached from a container or managed runtime.

Remediation. Replace with object storage or a managed file-transfer service, add a verified-transfer check (checksum plus row count) and record the transfer in the audit trail.

Evidence: importPendingFiles, parseCsv, archive, inbox, archive, dir, logo, name

LOW User identity carried in a server-side session

n/a - architectural readiness, not a compliance gap

The acting user is read from the servlet session. Horizontal scaling needs sticky sessions or a shared session store, and a lost session can leave a GxP write without an attributable actor.

Remediation. Carry identity in a signed token validated per request, and resolve the actor at the point of the write.

Evidence: create, assignRole, release, reject, enter, correct, approve, reject (+4 more)

5. Shadow / differential testing plan

Run the legacy and modernized components side by side. Mirror a copy of each production request to the new service, compare the responses field by field, and report every mismatch. The legacy system remains the system of record throughout, so a mismatch is a finding rather than a deviation.

Duration. Minimum two full business cycles per wave, and at least one month-end and one batch-release cycle for any HIGH-tier component.

Comparison rules

  • Response payloads compared field by field; a differing field is a finding.
  • Timestamps compared for ordering and timezone, not exact equality - clock source differences are expected and are themselves a finding to resolve.
  • Generated identifiers excluded from equality but checked for uniqueness and format.
  • Rounding of numeric results compared to the full stored precision: an OOS decision must not change because of a display rounding difference.
  • Audit-trail entries compared for presence, attributability and content.

Exit criteria

  • Zero unexplained mismatches on HIGH-tier endpoints over the full shadow period.
  • Every mismatch either resolved or accepted with a documented justification approved by QA.
  • Performance of the new service within the agreed envelope under production-equivalent load.

8. Rollback plan

Trigger criteria

  • Any mismatch on a HIGH-tier function that cannot be explained within the cutover window
  • Any GxP record written without a corresponding audit-trail entry
  • Data-migration reconciliation failing after cutover
  • Loss of attributability for any write (an actor cannot be resolved)
  • Performance outside the agreed envelope such that operations cannot proceed

Procedure

  1. Stop new work entering the modernized component; queue inbound requests.
  2. Re-point the facade or API gateway to the legacy implementation.
  3. Export every record created or modified in the modernized component since cutover, with its audit trail.
  4. Reconcile and replay those records into the legacy system under change control - they are GxP records and may not be discarded.
  5. Verify audit-trail continuity across both the cutover and the rollback.
  6. Raise a deviation, perform the investigation, and record the root cause.

Regulated data created after cutover

Records created in the modernized component between cutover and rollback are regulated records. They must be preserved, reconciled into the system of record, and their audit trail must remain continuous and attributable across both transitions. Plan the export path before cutover, not during the incident.

Rollback window. Rollback must remain possible for at least one full business cycle after cutover; keep the legacy path warm and tested for that period.

Decision authority. System owner plus QA; for HIGH-tier components the Qualified Person is informed before any rollback of a release path.
